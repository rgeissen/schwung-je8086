# Do the LFOs actually work? — rig built, engine run still owed (2026-09-17)

The question was asked the way the arpeggiator one was, and it deserves the same
answer: a measurement, not an argument. This session built the instrument and
ran everything that needs no firmware. **The audio measurement has not been made
— this container has no JP-8000 ROMs**, so the verdict below is explicitly
partial.

## What was established here

- **Every LFO address in the module agrees with jeLib.** 33 keys — the 13 patch
  parameters, the 9 `ctl_*` and 9 `vel_*` modulation depths, and `up_lfo1_sync`
  / `lo_lfo1_sync` — checked against `jemiditypes.h` with the linear→packed
  conversion applied: `jp_lfo_check.py --audit`, all agree, nothing missing.
  Not proof that they *do* anything; it rules out the class of bug that killed
  the system area, where the parameter existed and the write had nowhere to go.
- **Nothing in the LFO chain is a stub.** `grep -i lfo` over `jeLib` finds only
  the address tables: the LFOs are generated inside the emulated firmware and
  the ESP ASICs, with no host-side model to be missing. That is what separates
  this from `KeyScanner::read()` (returns 0 forever, so the panel keyboard
  cannot press a key) and from RPS (selectable, and with no recorded phrase to
  play it is silent). **Being unable to observe a parameter is not the same as
  knowing it does nothing — a stub device is knowing**, and here there is no
  stub to point at.
- **The writes take the proven path.** All 13 patch LFO parameters are
  `JP_AREA_PATCH`, so `param_write_block` addresses them off `JP_ADDR_TEMP` —
  the same base as `cutoff`, whose 0-vs-127 render is the control that proved
  temp-area DT1s reach the firmware.
- **The detectors are calibrated.** `jp_lfo_check.py --selftest` recovers a
  5.3 Hz tremolo, a 3.1 Hz vibrato, a 7.7 Hz filter sweep and a 6.2 Hz auto-pan
  to within 0.01 Hz, and reports "flat" for every unmodulated control — including
  a saw a semitone off, which is the "wrong patch is not a modulation" trap that
  a spectral-similarity score walked into at 0.86.
- **`jp8000_render` builds and runs natively on x86-64 Linux** (`build-native/`),
  and refuses with `no rom in <dir>` — which is exactly where this stops.

## What is NOT established

**Whether any LFO modulates the audio.** No render was made, because the 8 v1.5
ROM `.mid` files are not in this container and cannot be. Everything above is
consistent with working LFOs and none of it is evidence of one. The arpeggiator
read back ON, from correct addresses, in a fully emulated code path, for a whole
session — while producing exactly one voice start.

## Run it where the ROMs are

```bash
cmake -S . -B build-native -DCMAKE_BUILD_TYPE=Release
cmake --build build-native --target jp8000_render -j"$(nproc)"
python3 src/tools/jp_lfo_check.py --audit       # no ROM needed
python3 src/tools/jp_lfo_check.py --selftest    # no ROM needed
python3 src/tools/jp_lfo_check.py --rom dist/jp8000/roms --out /tmp/jp8000_lfo
```

~30 six-second renders. On a Mac the boot is 0.5 s from `boot.snap`; on device
put the output under `/data/UserData/jp8000_test/`, never `/tmp`.

It checks, each against its own depth-at-zero control:

| check | what would fail it |
|---|---|
| `lfo1_pitch` / `lfo2_pitch` | pitch does not wobble in cents |
| `lfo1_filter` / `lfo2_filter` | spectral centroid does not sweep |
| `lfo1_amp` / `lfo2_amp` | amplitude envelope does not pulse |
| `lfo1_pan` | L−R balance does not move with `amp_lfo1_mode` = AUTO |
| `lfo1_rate_tracks` / `lfo2_rate_tracks` | measured Hz does not climb with the rate byte |
| `lfo1_sync_1/4`, `lfo1_sync_1/8` | synced LFO does not land on the tempo division |
| `lfo1_fade_delays` | fade does not delay the onset |
| `lfo1_waveforms` | a waveform produces nothing, or SQR does not step |
| `lfo2_dest_exclusive`, `lfo1_manualpan_static` | the two traps below |

The rate sweep and the tempo sync are the load-bearing ones: **they land the
audio on a number the patch never mentions**, the way 31 arp attacks at 0.405 s
landed on the performance's stored 74 BPM. A tremolo alone could be almost
anything; a tremolo at 2.00 Hz with the performance at 120 BPM and the rate byte
set to 20 is the LFO.

## Three ways a working LFO looks broken

Each is hardware behaviour, each is reachable from the module's own pages, and
each is checked so a future report can be told apart from a real failure:

1. **LFO2 has one destination at a time.** `lfo2_depth_select` (PITCH / FILTER /
   AMP) decides which of the three LFO2 depth bytes is live. Turning "Filter
   LFO2" on the Filter page does nothing while the LFO 2 page says PITCH — and
   the depth still reads back, because reads come from our image.
2. **`amp_lfo1_mode` = MANUAL turns the Amp LFO1 depth into a static pan
   position.** Same byte, no motion. OFF is tremolo, AUTO is auto-pan.
3. **`up_lfo1_sync` / `lo_lfo1_sync` live in the PART block, not the patch.**
   With a sync division set, the LFO follows the performance tempo and
   `lfo1_rate` stops mattering — and a bank preset can bring that in with it,
   so it is not necessarily anything the user set. `base_patch()` in the checker
   pins it OFF for exactly this reason; a rate sweep that forgot to would read
   as "the rate knob does nothing".

## If a route does fail

Read the printed Hz before believing the FAIL. A sync check landing on half or
double the expected rate is a division-semantics question, not a dead LFO. A
route that reports modulation in BOTH the on and off renders means the base
patch is not still — chorus and delay both move on their own, which is why
`base_patch()` zeroes them.
